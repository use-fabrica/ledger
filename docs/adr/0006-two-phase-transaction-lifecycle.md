# Two-phase transaction lifecycle

Transactions are created in a `pending` state that earmarks funds, and later transition to `posted` (final) or `voided` (released). Balances track posted and pending amounts separately, so spendable funds are posted-minus-pending-outgoing. We considered post-only-at-creation (simpler: holds modeled as real transfers into a "holds" account) and rejected it because first-class payment-provider integrations — Stripe/Razorpay/Paddle — are built on authorize-then-capture semantics, and simulating holds with transfers produces convoluted, hard-to-audit journals. The cost is a small state machine (`pending → posted | voided`) and two balance columns instead of one.
